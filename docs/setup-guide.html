Copado Story Verification Gate · Installation guide

Set up the Story Verification Gate in a new org

Do the eight steps in order. Each step tells you where to do it, how long it takes and what you should see when it has worked. Mark each step done as you go; your progress is kept in this browser.

Overview

What you are installing

Verify button

Sits on the User Story. It runs six checks on the feature branch through a Copado Function and records the result as Clean or Issues.

14 validation rules

Block Ready to Promote and Promote and Deploy until the story is verified and Clean, its pull request is approved and its tests pass.

GitHub webhook

Records each new commit on a feature/US-… branch. A commit after verification blocks promotion again and unchecks both boxes.

Prerequisites

Before you start

Make sure you have all of these. Every step below assumes them.

  • Copado is installed (namespace copado) with a pipeline, a project and an authenticated Git repository.
  • The Salesforce CLI (sf) is installed, and you are logged in as a user who can deploy metadata, run anonymous Apex and edit Sites.
  • You are an admin of the GitHub repository that Copado uses, so you can add a webhook.
  • A terminal is open in the project folder D:\copado-story-verification.
i
Placeholders

Wherever you see <alias> in a command, replace it with your org alias, for example RBKPIPEQA. Highlighted values are always ones you fill in.

Deploy the package

Command lineAbout 5 minutes

Deploys all 53 components in manifest/package.xml (Apex, the trigger, the popup, fields, permission sets and the 14 validation rules) and runs the six test classes.

  1. Run a dry run first

    This validates everything and runs the tests without changing the org.

    sf project deploy start --manifest manifest/package.xml --target-org <alias> --dry-run --test-level RunSpecifiedTests --tests StoryVerificationServiceTest --tests StoryVerificationCompleteTest --tests StoryVerificationControllerTest --tests StoryVerificationSetupTest --tests StoryVerificationMetadataControllerTest --tests StoryVerificationPushWebhookTest --wait 30

  2. Deploy for real

    When the dry run succeeds, run the same command without --dry-run.

    sf project deploy start --manifest manifest/package.xml --target-org <alias> --test-level RunSpecifiedTests --tests StoryVerificationServiceTest --tests StoryVerificationCompleteTest --tests StoryVerificationControllerTest --tests StoryVerificationSetupTest --tests StoryVerificationMetadataControllerTest --tests StoryVerificationPushWebhookTest --wait 30
✓
You should see

Status: Succeeded, 53 components deployed and all six test classes passing.

!
If the tests fail

The org's own validation rules on User Story can stop the test data from saving. The tests already fill Jira_Key__c. If another rule blocks them, extend the test data to satisfy it.

Create the Copado Function records

Command lineAbout 1 minute

The Copado Function, Job Template and Job Step are data records, not metadata, so the deploy cannot create them. One Apex call creates all three.

  1. Run the setup script

    sf apex run --file scripts/create-copado-records.apex --target-org <alias>
    or

    In the Developer Console, open Debug›Open Execute Anonymous Window and run:

    StoryVerificationSetup.run();
✓
You should see

The debug log contains Story Verification records ready. Function=… Template=… Step=…

3

Store the webhook secret

Salesforce SetupAbout 3 minutes

GitHub signs every delivery with a shared secret. Salesforce checks the signature against the secret stored in a custom metadata record.

  1. Generate a random secret

    PowerShell
    $b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b | % { $_.ToString('x2') })
    Git Bash, macOS or Linux
    openssl rand -hex 32

    Save the 64-character value in your password manager. You need it again in step 5.

  2. Create the Default record

    1. Go to Setup›Custom Metadata Types.
    2. Click Manage Records next to Story Verification Setting, then New.
    3. Fill in the fields below and click Save.
    FieldValue
    LabelDefault (exactly)
    Story Verification Setting NameDefault (exactly)
    GitHub Webhook Secretthe secret from 3a
!
Keep the secret private
  • Never send it by email or chat, and never commit it to Git.
  • To rotate it, change it here and in GitHub at the same time. Deliveries sent in between get a 401.
Default record saved?
4

Create the Site and give the guest user access

Salesforce SetupAbout 5 minutes

GitHub needs a public URL to call. A Salesforce Site provides it, and the site's guest user receives each delivery.

  1. Create the Site

    1. Go to Setup›Sites. If this is the org's first site, register a Sites domain first.
    2. Click New, fill in the fields below and click Save.
    FieldValue
    Site Labelstoryverification
    Site Namestoryverification
    Default Web AddressLeave empty
    Active Site Home PageAny page, for example InMaintenance
    ActiveChecked

    You can reuse an existing active site instead of creating a new one.

  2. Give the guest user the webhook permission set

    1. Open the site and click Public Access Settings.
    2. Click View Users, then open Site Guest User.
    3. Under Permission Set Assignments, click Edit Assignments, add Copado Story Verification Webhook and save.
    i
    Why this is safe

    The permission set only grants access to the StoryVerificationPushWebhook class and create on the Story_Branch_Push__e event. The guest user never reads or edits stories. The trigger that updates stories runs as the Automated Process user.

  3. Write down the endpoint URL

    Copy the site's domain from the Sites page and build the URL:

    https://<site domain>/services/apexrest/storyverification/push
    • A sandbox domain looks like https://<org>--<sandbox>.sandbox.my.salesforce-sites.com.
    • If the site has a path, put it before /services: https://<domain>/<path>/services/apexrest/storyverification/push.
Site active, guest user assigned, URL noted?

Add the GitHub webhook

GitHubAbout 3 minutes

From now on every push to the repository is sent to Salesforce, which records the new head commit on the matching story.

  1. Create the webhook

    1. In the repository, go to Settings›Webhooks and click Add webhook.
    2. Fill in the fields below and click Add webhook.
    FieldValue
    Payload URLthe endpoint URL from 4c
    Content typeapplication/json
    Secretthe same secret as step 3
    SSL verificationEnable
    Which events?Just the push event
    ActiveChecked

  2. Check the ping

    Open the webhook, go to the Recent Deliveries tab and open the ping delivery.

Add the Verify button to the page layout

Salesforce SetupAbout 3 minutes

Page layouts are not in the package, because deploying one would overwrite your org's layout. Add the button by hand.

  1. Add the action

    1. Go to Setup›Object Manager›User Story›Page Layouts and open the layout your users use.
    2. From Mobile & Lightning Actions in the palette, drag Verify (Verify_Story_Live) into the Salesforce Mobile and Lightning Experience Actions section.
    3. Click Save.

  2. Optional: add the result fields

    Add Verification Status, Verification Date and Verification Details to the layout so users can see the last result.

i
Dynamic actions

If the record page uses dynamic actions, add Verify in Lightning App Builder instead.

8

Run the smoke test

Salesforce and GitHubAbout 5 minutes

Use a test story that has a feature/US-… branch. Do each action in order and compare with the expected result.

  1. Do

    Check Ready to Promote without verifying the story.

    Expect

    Blocked: "This User Story has not been verified. Run Verify before Promote."

  2. Do

    Click Verify.

    Expect

    Six checks run and the verdict is Clean or Issues.

  3. Do

    On a Clean story, check Ready to Promote.

    Expect

    Saves, as long as the pull request is approved and Pending Tests is 0.

  4. Do

    Uncheck it. Then commit directly on GitHub to the story's feature/US-… branch.

    Expect

    The delivery shows 200 Recorded US-… at <sha> and Branch Head SHA updates on the story.

  5. Do

    Check Ready to Promote, then Promote and Deploy.

    Expect

    Both blocked: "The feature branch has changed since the last verification. Run Verify again before Promote."

  6. Do

    Click Verify again, then check Ready to Promote.

    Expect

    Saves.

  7. Do

    With Ready to Promote checked, commit again on GitHub and refresh the story.

    Expect

    Ready to Promote and Promote and Deploy are both unchecked automatically.

✓
All seven match?

The gate is fully installed. If one doesn't match, see Troubleshooting.

Later

Upgrading later

Steps 3 to 7 are one-time. For a new version you only repeat steps 1 and 2.

  1. If function/index.js changed, rebuild the setup script

    node scripts/build-create-records.js
node scripts/build-create-records.js --check

  2. Redeploy the package

    Run the deploy in step 1.

  3. Rerun the setup script

    Run step 2 so the Function uses the new code.

Help

Troubleshooting

Find the message or symptom you see, then apply the fix.

"Invalid template name Story_Verification_1"

The Copado records don't exist yet. Run step 2.

"You do not have access to this story"

Assign the Copado Story Verification User permission set (step 7).

"Repository not authenticated"

Re-authenticate the Git repository in Copado, then rerun step 2.

Stuck on "Waiting for Copado to start the job"

The Copado job queue is busy. Wait, or click Cancel next to Close. That marks the story Failed ("Verification cancelled by …") and ignores the job's result when it arrives.

Webhook returns 200 but Branch Head SHA doesn't update

Only feature/US-… branches are recorded. If a Copado trigger rejects the Automated Process user, add a PlatformEventSubscriberConfig for StoryBranchPushTrigger that runs as a Copado-licensed integration user.

Ready to Promote stays checked after a direct commit

Same cause as above, or another validation rule refused the uncheck. The new head commit is still saved, so checking the box again stays blocked until the story is verified again.

"All tests on this User Story must pass before Promote."

Pending Tests is above 0. Run the story's tests and make sure they pass.
