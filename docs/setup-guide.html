Setting up the Story Verification Gate in a new org

Eight steps, in order. Steps 1 and 2 are commands; steps 3 to 8 are clicks in Setup and GitHub. Tick each step as you finish it; the ticks stay in this browser only.

Before you start

  • The org has Copado installed (namespace copado) with a pipeline, a project and a Git repository that shows as authenticated.
  • You have the Salesforce CLI (sf) and a user who can deploy metadata, run anonymous Apex and edit Sites.
  • You are an admin on the GitHub repository (needed to add a webhook).
  • Open a terminal in D:\copado-story-verification. Replace <alias> below with your org alias, for example RBKPIPEQA.
1

Deploy the package

Command line · about 5 minutes

The manifest manifest/package.xml holds everything this utility needs as metadata: 53 components. It was checked against every file under force-app/ and nothing is missing (full list and the file itself are at the end of this page).

a. Check-only run first

sf project deploy start --manifest manifest/package.xml --target-org <alias> --dry-run --test-level RunSpecifiedTests --tests StoryVerificationServiceTest --tests StoryVerificationCompleteTest --tests StoryVerificationControllerTest --tests StoryVerificationSetupTest --tests StoryVerificationMetadataControllerTest --tests StoryVerificationPushWebhookTest --wait 30

b. Real deployment

Same command without --dry-run:

sf project deploy start --manifest manifest/package.xml --target-org <alias> --test-level RunSpecifiedTests --tests StoryVerificationServiceTest --tests StoryVerificationCompleteTest --tests StoryVerificationControllerTest --tests StoryVerificationSetupTest --tests StoryVerificationMetadataControllerTest --tests StoryVerificationPushWebhookTest --wait 30
Success looks like: Status: Succeeded, 53 components deployed, all six test classes passing.
If tests fail with a required-field or validation error on User Story, the org has its own validation rules (for example a mandatory Jira key). The tests already fill Jira_Key__c when it exists; for other rules extend the test data in the test classes.
2

Create the Copado Function (post-deployment Apex)

Command line · 1 minute

The Copado Function, Job Template and Job Step are data records, not metadata, so they cannot be in package.xml. The class StoryVerificationSetup (deployed in step 1) creates them.

sf apex run --file scripts/create-copado-records.apex --target-org <alias>

Or paste this one line into Developer Console → Debug → Open Execute Anonymous Window:

StoryVerificationSetup.run();
Success looks like: the debug log shows Story Verification records ready. Function=… Template=… Step=…
Record createdAPI nameNotes
Copado FunctionStory_VerificationImage copado-multicloud-dx:v6, worker size S
Job TemplateStory_Verification_1Started by the Verify popup
Job StepStory_Verification_1_Story_Verification_1Runs the Function
Safe to run again: it updates the records in place. Run it again after every new deployment of the package, because the Function's code lives inside StoryVerificationSetup.
3

Create the custom metadata record (webhook secret)

Setup · 3 minutes

The webhook checks every GitHub delivery against a shared secret. The secret is kept in a custom metadata record that is not in the repository, on purpose, so it never lands in Git.

a. Generate a secret

In PowerShell (cryptographically random, 64 hex characters):

$b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b | % { $_.ToString('x2') })

or in Git Bash: openssl rand -hex 32. Keep it somewhere safe (a password manager); you will paste it again in step 5.

b. Create the record

  1. Setup → Custom Metadata Types → Story Verification Setting → Manage Records → New.
  2. Label: Default · Story Verification Setting Name: Default (it must be exactly Default; the webhook looks it up by that name).
  3. GitHub Webhook Secret: paste the secret. Save.
Never send the secret by email or chat. To rotate it later, change it here and in GitHub (step 5) at the same time; deliveries in between get 401.
4

Create the Site and give its guest user access

Setup · 5 minutes

GitHub needs a public URL to call. A Salesforce Site exposes the Apex REST class StoryVerificationPushWebhook without a login; the signature check from step 3 keeps it safe.

a. Create the site

  1. Setup → Sites. If this is the first site in the org, register a Sites domain when asked (once per org).
  2. New: Site Label storyverification, Site Name storyverification, leave Default Web Address empty (or note the path if you set one), pick any Active Site Home Page (for example InMaintenance), tick Active. Save. An existing site can be reused instead.

b. Give the guest user the webhook permission set

You do not create this user. Salesforce creates the site's guest user automatically when you save the site in 4a; package.xml creates no users. You only assign it one permission set:

  1. On the site's page click Public Access Settings → View Users → open the Site Guest User.
  2. Permission Set Assignments → Edit Assignments → add Copado Story Verification Webhook → Save.

That permission set gives only two things: access to the class StoryVerificationPushWebhook and create on the platform event Story_Branch_Push__e. The guest user never reads or writes User Stories; the event's trigger does that as the Automated Process user.

c. Write down the endpoint

https://<site domain>/services/apexrest/storyverification/push

The site domain is shown on the Sites page. In a sandbox it looks like https://<org>--<sandbox>.sandbox.my.salesforce-sites.com. If the site has a path, add it: https://<domain>/<path>/services/apexrest/storyverification/push.

5

Add the webhook in GitHub

GitHub repository settings · 3 minutes
  1. Open the repository connected to the Copado pipeline → Settings → Webhooks → Add webhook.
  2. Fill in:
    FieldValue
    Payload URLthe endpoint from step 4c
    Content typeapplication/json
    Secretthe same secret as step 3
    SSL verificationEnable
    Which eventsJust the push event
    Activechecked
  3. Add webhook. GitHub sends a ping at once.
Success looks like: webhook → Recent Deliveries shows the ping with response 200 and body {"message":"pong"}.
ResponseMeaning and fix
401 Invalid signatureThe secret in GitHub differs from the Default record. Re-paste the same secret in both places.
500 Webhook secret is not configuredThe Default record is missing, misnamed or has an empty secret (step 3).
404Wrong URL or site path, or the site is not Active.
403 or an HTML login pageThe guest user lacks the Copado Story Verification Webhook permission set (step 4b).
200 Ignored: not a story feature branch updateNormal for pushes to any branch other than feature/US-… and for branch deletions.
6

Put the Verify button on the User Story page

Setup · 3 minutes
  1. Setup → Object Manager → User Story → Page Layouts → open the layout(s) your teams use.
  2. In Mobile & Lightning Actions, drag Verify (Verify_Story_Live) into Salesforce Mobile and Lightning Experience Actions. Save.
  3. Optional: add Verification Status, Verification Date and Verification Details to the layout or Lightning record page so the verdict is visible without opening the popup.
If the record page uses dynamic actions instead of the layout, add the Verify action in Lightning App Builder on the record page's highlights panel.

Assign permission sets

Setup or command line
WhoPermission set(s)What they get

Emergency users who may skip the gate (as few as possible)Bypass + UserAll 14 validation rules switched off for them.

From the command line:

sf org assign permset --name Copado_Story_Verification_User --target-org <alias> --on-behalf-of <username>
Release managers can get the bypass through your own permission set group instead: add the custom permission Bypass_Verification_Gate to it. No rule needs editing.
8

Smoke test

In the org, about 10 minutes
#Do thisExpect
1Open a story with commits and check Ready to Promote without verifying.Blocked: "This User Story has not been verified."
2Click Verify → Verify in the popup.Six checks run live; verdict Clean or Issues with reasons.
3On a Clean story, check Ready to Promote.Saves (if PR approved and Pending Tests = 0).
4Uncheck it, then commit a change directly on GitHub to feature/US-….GitHub delivery 200 "Recorded US-… at <sha>"; story's Branch Head SHA updates within seconds.
5Check Ready to Promote, then Promote and Deploy.Both blocked: "The feature branch has changed since the last verification."
6Verify again, then check Ready to Promote.Saves: verified SHA now equals branch head.
7With Ready to Promote still checked, commit another change directly on GitHub to the same branch, then refresh the story.Ready to Promote and Promote and Deploy are both unchecked automatically.
When all seven behave as expected, the gate is live.

Upgrading later

  1. If function/index.js changed: node scripts/build-create-records.js then node scripts/build-create-records.js --check.
  2. Deploy package.xml again (step 1).
  3. Run StoryVerificationSetup.run(); again (step 2). Steps 3 to 7 are one-time and do not need repeating.

Troubleshooting

What you seeCause and fix
Invalid template name Story_Verification_1Step 2 was not run in this org. Run it.
You do not have access to this storyUser lacks Copado Story Verification User (bypass users need it too).
Repository not authenticatedRe-authenticate the Git repository in Copado, then rerun step 2.
Stuck on "Waiting for Copado to start the job"Copado's own queue; varies from seconds to a few minutes. To give up, click Cancel beside Close: the story is marked Failed ("Verification cancelled by …") and stays blocked until it is verified again. The Copado job may still finish, but its result is ignored.
Webhook 200 but Branch Head SHA does not updateOnly feature/US-… branches are recorded. If Copado triggers reject the Automated Process user, add a PlatformEventSubscriberConfig for StoryBranchPushTrigger running as an integration user with a Copado licence; errors are in the debug log.
Ready to Promote stays checked after a direct GitHub commitSame cause as the row above, or another validation rule or trigger refused the uncheck (the error is in the debug log). The new branch head is still saved, so a re-check stays blocked until Verify runs again.
"All tests on this User Story must pass before Promote."The story's Pending Tests is above 0. Run the tests and make sure they pass; Verify does not clear it.
