## Facts about how Copado Functions work (confirmed from the org's own standard Functions)
- Git access: step parameter `git_json` = `{$Context.Repository.Credential}` (a JSON string with at least `url`). In the script, `copado-git-get --depth "<N>" "<branch>"` clones/fetches the repository into the current directory and checks out that branch; `copado-git-get -g "<any git command>"` runs a git command with the credentials injected (`ls-remote`, `fetch origin <b> --depth N`, `push`). After that plain `git` commands work in the working directory. Also pass `gitDepth` (string, default "200") like Copado's own steps. Do NOT hardcode credentials; never print `git_json`.
- Progress: `copado -p "<text>"` (shown live in the popup via Result.copado__Progress_Status__c, latest message only).
- RESULT: use the long flag. The current script calls `copado -r <json>`; that flag is wrong/unreliable, which is why no result ever came back. Correct usage (from Copado's own Function): `copado --progress "Process finished..." --result-data '<json>'`. Call it via `execFileSync("copado", ["--progress", "...", "--result-data", jsonString])` (no shell). Also print a final line `RESULT:<json>`. The result lands in `copado__Result__c.copado__Result_Data__c` (max 131072 chars: cap lists so the JSON stays well under ~100000 chars).
- The Function script is stored in `copado__Script__c`, must start with `#!/usr/bin/env node`, runs in image `copado-multicloud-dx:v6` (Node + git available).
- `copado.CreateExecution.Request` has these properties (confirmed from the symbol table): `templateName, transactionId, parentId, pipelineId, sourceId, destinationId, callback, dataJson, preSteps, postSteps, additionalSteps, runAfterInstantiation, jobStepId`. Copado's own jobs set `pipelineId` (and `sourceId` = the story's environment) so `{$Context.Repository...}` resolves; we must set them too.
- Story -> pipeline: `copado__User_Story__c.copado__Project__r.copado__Deployment_Flow__c`; source environment: `copado__User_Story__c.copado__Environment__c`. Pipeline steps: `copado__Deployment_Flow_Step__c` (fields `copado__Deployment_Flow__c`, `copado__Branch__c` = source env branch, `copado__Destination_Branch__c`, `copado__Source_Environment__c`, `copado__Destination_Environment__c`). The org/env branch names = distinct non-blank `copado__Branch__c` and `copado__Destination_Branch__c` over the story's pipeline steps (lowercase compare), same idea as runner.mjs 944-960.
- Branch convention: feature branch = `feature/<story Name>`; base branch = `copado__Base_Branch__c` (fall back to `main` if blank; the validator falls back to `origin/master` — here use the first of base, `main`, `master` that exists on the remote).
- Registered commits: `copado__User_Story_Commit__c` where `copado__User_Story__c = :id` — SHA is `copado__Snapshot_Commit__r.copado__Commit_Id__c`; `copado__Status__c = 'Complete'` are registered; others (status != Complete) are "non-complete" records with their status. Registered metadata: `copado__User_Story_Metadata__c` (`copado__Metadata_API_Name__c`, `copado__Type__c`), lowercase names; `hasCustomLabelMetadata` = any record with Type `CustomLabel` (case-insens).

## 2. Function `function/index.js` (rewrite; keep it well under ~14000 characters, plain readable JS, no secrets in logs)
Environment: `git_json, gitDepth, runId, storyName, featureBranch, baseBranch, envBranchesJson, registeredCommitsJson, nonCompleteCommitsJson, registeredMetadataJson, hasCustomLabelMetadata, findings` (+ the existing ones). Parse JSON strings defensively (also accept already-parsed arrays).
Flow, with a `copado -p` progress message at the start of EACH phase and a short summary per check:
1. Progress "Cloning repository…": `copado-git-get --depth N "<featureBranch>"`; on failure the whole run result is `Failed` (not Issues) with the error (redact anything credential-like). Then make sure refs exist locally: `git fetch origin <base> --depth N` and each env branch via `copado-git-get -g "git fetch origin <b> --depth N"` (ignore a missing env branch, note it). Deepen history (`git fetch --deepen=200`, via copado-git-get -g, at most 5 times) until `git merge-base origin/<base> HEAD` succeeds; if never, report check results as `skipped` with that reason rather than guessing.
2. **Check "Org/environment branch merge"** (id `org-branch-merge`): port runner.mjs 1154-1210: over `git log --first-parent --format=%H%x00%P%x00%s origin/<base>..HEAD`, Method A: subject matches `Merge (remote-tracking )?branch '<name>'` where name (lowercase) is one of the env branches; Method B (only if A found nothing): for merge commits take the second parent and, for each env branch, `git merge-base --is-ancestor <secondParent> origin/<env>` and NOT already an ancestor of `origin/<base>`. Result `fail` with one line per detection (`merged <branch> in commit <sha10>`), otherwise `pass` ("No environment branch was merged into the feature branch"). If this check fails, the other two checks are `skipped` with reason "skipped because an environment branch merge brings in unrelated commits" (this mirrors the validator's fast-fail).
3. **Check "Unregistered commits"** (id `unregistered-commits`): `git log --format=%H origin/<base>..HEAD` = extra commits. If there are none -> `fail` "Feature branch has no commits beyond <base>" (nothing to promote). Unregistered = extra commits whose SHA is not in the registered (Complete) SHA set (compare exact, case-insensitive; also accept one being a prefix of the other). For each unregistered commit collect sha10, author name/email, committer email, commit subject, files (`git diff-tree --no-commit-id -r --name-only <sha>`), components (use `parseApiName`, copied from runner.mjs line 148 into the script), covered/uncovered components with `isCovered` exactly as runner.mjs 1318-1324 (exact name or `name.` prefix match against registered metadata, plus `customlabels` covered when `hasCustomLabelMetadata`). Exempt "Copado auto" commits whose subject starts with `Updated sourceApiVersion from`, `Clear custom_rulesets in code-analyzer.yml` or `Add custom PMD rules to custom-rules-list.txt`. Verdict (mirror runner.mjs 1649-1665): no unregistered (after exemptions) -> `pass`; any unregistered commit matching a non-complete Copado commit record whose status is not `Failed` -> `fail` (hard block, name the status); any uncovered components -> `fail`; all covered but an author differs from the authors of the registered commits -> `fail` with "needs manual verification: commit by <author> (not a registered committer)"; all covered and same author -> `warn` ("N commit(s) made outside Copado; every component is registered on the story and the author is the same"). Details list one line per unregistered commit: `<sha10> <author> "<subject>" — uncovered: a, b` (cap 50 commits, 30 components each, and say "+N more").
4. **Check "Metadata coverage"** (id `metadata-coverage`): components changed on the branch overall: `git diff --name-only origin/<base>...HEAD` (three-dot; fall back to two-dot if no merge base), mapped with `parseApiName` (ignore files not under `default/`), deduped. Covered/uncovered with the same `isCovered`. `fail` if any uncovered (list them, cap 100: "changed in git but not registered on the story — add them in Copado or the promotion will miss them"); `pass` otherwise ("All N changed components are registered"). Additionally list informationally (does not change the status) registered metadata that is not in the branch diff: `registered on the story but unchanged in git: x, y` (cap 50).
5. Also pass through the Apex-computed `findings` unchanged (they stay in the result as `salesforceFindings`) so nothing is lost.
6. Result JSON: `{"runId", "status": "Clean"|"Issues"|"Failed", "details": "<newline lines>", "checks": [{"id","title","status": "pass"|"fail"|"warn"|"skipped","summary","lines":["…"]}], "salesforceFindings": [...]}`. `status` is `Issues` if any check `fail` or any Apex finding is severity `issue`, else `Clean` (`warn` and `skipped` do not make it Issues, but `skipped` due to a clone/merge-base problem should add a line to `details`). `details` is a readable multi-line rendering of everything (Apex findings first, then each check title, its status word and its lines). Keep `checks[].lines` capped so the whole JSON is < 100000 chars.
7. Output with `copado --progress "Verification finished" --result-data <json>` (long flags, execFileSync, no shell) AND `console.log("RESULT:" + json)`; on any uncaught error emit a `Failed` result with the message and exit 1.
